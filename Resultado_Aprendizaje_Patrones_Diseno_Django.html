1 Identificación del Modelo de Arquitectura

El proyecto Django implementa una Arquitectura en Capas (Layered Architecture) construida sobre el patrón fundamental MVT (Model-View-Template / Model-View-Controller en Django REST), al cual se le ha incorporado una Capa de Servicios (Service Layer) para encapsular la lógica de negocio y desacoplarla de los controladores HTTP.

Esta arquitectura establece límites bien definidos entre responsabilidades:

  • Capa de Enrutamiento (urls.py): Punto de entrada que recibe las solicitudes HTTP entrantes y las redirige hacia la vista o controlador correspondiente.
  • Capa de Vistas / Fachada (views.py): Valida la autenticación mediante JWT, extrae parámetros HTTP, actúa como punto de acceso simplificado (patrón Facade) delegando el trabajo pesado a la capa de servicios, y serializa la respuesta JSON.
  • Capa de Servicios (services.py): Nueva capa donde reside la lógica de negocio pura (algoritmos de descuento según categoría mediante el patrón Strategy), independiente de la base de datos o de la interfaz HTTP.
  • Capa de Modelos / Persistencia (models.py): Define las entidades del dominio, las relaciones en base de datos relacional y proporciona métodos de creación controlada mediante el patrón Factory Method.
DIAGRAMA DE ARQUITECTURA EN CAPAS Y FLUJO DE UNA PETICIÓN HTTP
Flujo desacoplado: Petición entrante → Enrutamiento → Fachada orquestadora → Estrategia de cálculo → Persistencia ORM → Respuesta JSON.
2 Capa de Servicios y Patrón de Comportamiento: Strategy

Se creó el archivo products/services.py donde se aloja la lógica de negocio pura. Se implementó el patrón de comportamiento Strategy, el cual permite definir una familia de algoritmos de descuento, encapsular cada uno en su propia clase y hacerlos intercambiables según la categoría del producto:

products/services.py — Patrón Strategy Python 
# products/services.py

class EstrategiaDescuento:
    def calcular(self, precio):
        raise NotImplementedError


class DescuentoElectronica(EstrategiaDescuento):
    def calcular(self, precio):
        return precio * 0.90  # 10% de descuento


class DescuentoRopa(EstrategiaDescuento):
    def calcular(self, precio):
        return precio * 0.80  # 20% de descuento


class SinDescuento(EstrategiaDescuento):
    def calcular(self, precio):
        return precio         # 0% de descuento


def obtener_estrategia(categoria_nombre):
    estrategias = {
        'Electronica': DescuentoElectronica(),
        'Electrónica': DescuentoElectronica(),
        'Ropa': DescuentoRopa(),
    }
    return estrategias.get(categoria_nombre, SinDescuento())
Beneficio Arquitectónico (Principio Open/Closed):
Para incorporar nuevas reglas o promociones en el futuro (ej. "Hogar" o "Deportes"), basta con agregar una nueva subclase en services.py sin modificar las vistas ni los modelos existentes.
3 Patrón Creacional: Factory Method en models.py

En products/models.py se incorporó a la clase Product el método de clase crear_con_categoria_default. Este método implementa el patrón Factory Method, encapsulando y estandarizando la instanciación de productos garantizando una categoría predeterminada ('Sin categoría') si no se especifica una:

products/models.py — Patrón Factory Method Fragmento de Product 
# products/models.py (extracto dentro del modelo Product)

    @classmethod
    def crear_con_categoria_default(cls, name, description, price):
        categoria_default, _ = Category.objects.get_or_create(name='Sin categoría')
        return cls.objects.create(
            name=name,
            description=description,
            price=price,
            category=categoria_default
        )
4 Patrón Estructural: Facade (Fachada) en views.py y urls.py

En products/views.py se implementó la función precio_final con el decorador @api_view(['GET']) y protección JWT mediante @permission_classes([IsAuthenticated]). Esta vista actúa como una Fachada (Facade) al unificar y ocultar la complejidad de la consulta al ORM, la resolución de la estrategia de descuento y el redondeo monetario en una única interfaz simple:

products/views.py — Patrón Facade DRF Function-Based View 
from rest_framework.decorators import api_view, permission_classes
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response
from .models import Product
from .services import obtener_estrategia

@api_view(['GET'])
@permission_classes([IsAuthenticated])
def precio_final(request, pk):
    producto = Product.objects.get(pk=pk)
    estrategia = obtener_estrategia(producto.category.name)
    precio_con_descuento = estrategia.calcular(float(producto.price))
    return Response({
        'producto': producto.name,
        'precio_original': producto.price,
        'precio_final': round(precio_con_descuento, 2)
    })
products/urls.py — Registro de la ruta Enrutador 
from django.urls import path, include
from .views import CategoryViewSet, ProductViewSet, precio_final
from rest_framework.routers import DefaultRouter

router = DefaultRouter()
router.register('products', ProductViewSet, basename='products')
router.register('categories', CategoryViewSet, basename='categories')

urlpatterns = [
    path('', include(router.urls)),
    path('products/<int:pk>/precio-final/', precio_final, name='precio-final'),
]

Método de clase crear_con_categoria_default 		Pertenece a la categoría creacional porque encapsula la lógica de instanciación del objeto Product. Clases EstrategiaDescuento y obtener_estrategia 		Pertenece a la categoría de comportamiento porque define una familia de algoritmos de cálculo de descuentos intercambiables en tiempo de ejecución. Permite variar dinámicamente el comportamiento de cálculo según la categoría del producto, desacoplando la lógica de negocio de los controladores.
9 Conclusiones y Beneficios Arquitectónicos

La incorporación de la Capa de Servicios y la aplicación de los tres patrones de diseño (Factory Method, Facade y Strategy) aportan ventajas sustanciales a la arquitectura de la aplicación:

  • Principio de Responsabilidad Única (SRP): Las vistas en views.py únicamente se encargan de gestionar el protocolo HTTP y autenticación, mientras que la lógica de cálculo financiero reside exclusivamente en services.py.
  • Principio Abierto / Cerrado (OCP): Se pueden agregar nuevas reglas comerciales creando nuevas estrategias de descuento sin necesidad de modificar el código existente en las vistas ni en los modelos.
  • Alta Cohesión y Bajo Acoplamiento: Cada componente del sistema tiene un propósito único y se comunica a través de interfaces claras, facilitando el mantenimiento y las pruebas automatizadas.
  • Seguridad por Capas: El acceso a la fachada está protegido por tokens JWT, garantizando que solo clientes autorizados puedan interactuar con la lógica del negocio.
